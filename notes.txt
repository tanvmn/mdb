WEB APPLICATION STRUCTURE

- A server, in a loop, listens for incoming requests from clients to accept connections.
- When a connection is accepted, the request is routed to the corresponding registered handler based on the request's path.
- After processing the request, the server responses to the client.

So a web application needs:
- a multiplexer to register handlers with request's path patterns and maybe request's methods.
- something to announce an ip address (host:port) on the local network.
- a server to listen for requests on an ip address, to accept connections, and to response to clients.

MODULE
- When there is a valid go.mod file at the root the progject, the project becomes a module.
- When using go get to download dependencies into the project, the exact version of the downloaded dependecies are recorded in go.mod.
	This ensures the project's reproducibility when building to binary or running.
- When you run or build the project, Go uses the exact versions of dependencies listed in go.mod.
	If any dependencies aren't in your local machine, Go will automatically download them, along with any recursive dependencies (dependencies of the dependencies?).
- The go.mod file also defines the module path, which is the identifier for the module.
	The module path is also the root of the import path for any non-standard packages.

API VERSIONING
APIs in real-world businesses often need to change their functionality, sometimes in backwards-incompatible way.
To avoid problems for clients, it's a good idea to implement some form of API versioning. That way, clients can choose their suitable version.
This service versions API by prefixing all endpoints with "/v*" like "/v1/healthcheck".

HTTP METHOD
GET: for actions that retrieve resource only and don't change the state of the application or the data.
POST: for non-idempotent actions that modify state. In context of REST API, POST is generally used for creating a new resource.
PUT: for idempotent actions that modify state of a resource at a specific URL. In context of REST API, PUT is generally used for updating or replacing an existing resource.
PATCH: for actions that partially update a resource at a specific URL. The action can be either imdempotent or non-idempotent.
DELETE: for actions that delete a resource at specific URL.

JSON ENCODING IN GO

- chan, func, complex* values cannot be encoded into JSON. If try, json.UnsupportedTypeError will be returned.
- for any pointer values, the values pointed to will be encoded.
- time.Time value will be encoded to JSON string in RFC3339 format.
- []byte value will be encoded to base64-encoded JSON string.

JSON struct tag directives:
- "-": don't encode.
- "omitzero": don't encode field that has its type's zero value.
- "omitempty":
	. don't encode field that has non nil value but len is zero.
	. won't omit struct (including time.Time) whose all fields are zero or empty values.
	. won't omit array even all element values are zero or empty.
	. omits empty or zero maps and slices.
	. for now, use if need to omit empty slices and maps.
- "string": encode numerics and bool (or pointers to them) to string.

SYSTEM GENERATED ERROR RESPONSE

http.Server can automatically serves plain-text when a request:
- specifies supported HTTP version.
- sends HTTP to HTTPS server.
- has a missing or invalid Host header or has multiple Host header.
- has an empty Content-Length header.
- has unsupported an Transfer-Endcoding header.
- has size that exceeds MaxHeaderBytes setting.

CONNECTION POOL OF SQL.DB

- sql.DB connection pool has 2 type of connections: idle and in-use.
- a connection is marked as in-use when it's being used to perform a database task. When the task in completed, the connection is marked as idle.
- when Go is instructed to do a database task, it looks for an idle conn in the pool.
	  If none is found, Go creates a new one. If one is found, Go reuses it and marks as "in-use".
- when an idle conn is reused, Go gracefully handles any problems with it.
	  A bad conn is re-tried twice before giving up, at which point, Go removes the bad one and creates a new one.

Configuring the pool by using methods of *sql.DB:
	- SetMaxOpenConns:
		. sets DBStats.MaxOpenConnections (MOC) (default=0 <-> unlimited). If MaxIdleConns (MIC) > 0 && MOC < MIC, MIC is reduced to MOC.
		. MOC = idle + in-use conns in sql.DB pool.
		. these conns are used to communicate with db, which manages its own pool of conns. By default, postgres' max conns are set by max_connections=100 in postgres.conf.
		. if MOC > max_connections, there could be a case postgres responses error "sorry, too many clients already".
			Therefore, MOC should be < max_connetions leaving some room for other processes to communicate with postgres.
		. MOC could be:
			_ bottleneck if too low
			_ denied by postgres if too high
		. if all of MOC are in-use, a new db task could wait forever for a conn to be available. Therefore, use context to timeout db tasks.

	- SetMaxIdleConns:
		. set MaxIdleConns (MIC) limit int sql.DB pool.
		. high MIC could be beneficial cause fewer conns may likely need to be created.
		. high MIC could not be beneficial cause if a conn is idle too long, it could become unusable cause the corresponding db conn may be closed.
		. high MIC could hoard memory that could be used by the app, db.
		. SHOULD just keep the conn idle when it's likely gonna be used again soon.
		. SHOULD be <= MOC cause Go will reduce MIC to MOC if MIC > MOC.

	- SetConnMaxLifetime:
		. set MaxConnLifetime (MCL), the duration after which, since first created, a conn, if idle, will be expired.
		. by default, MaxConnLifetime is unlimited, so a conn could be reused forever.
		. a conn isn't nessessarily expired after MCL cause it could be unusable before.
		. a conn could be in-use after MCL, so when becomes idle, it'll be expired.
		. periodically, Go runs a background cleanup operation to removed expired conns.
		. set MCL unlimited could help make it less likely new conns will need to be created
		. set MCL finite could help prevent being denied from db cause db could enforce a finite MCL on its own conns.
		. set MCL finite could make it easier to swap db gracefully behind a load balancer.
			(I assume gracefully here means waiting for db to finish all ongoing tasks before swapping; don't know what "easier" here is about)
		. if MCL is finite, bear in mind the frequency of conns being removed and created.
			If there are 100 open conns, and MCL is 1min, an average of 1.67 conns could be removed and created every second.
			A frequency that great isn't desired cause it hinders performance.

	- SetConnMaxIdleTime:
		. set MaxConnIdleTime (MCIT), the duration after which, since first idle, a conn'll be expired.
		. by default, MCIT is unlimited.
		. MCIT helps set MaxIdleConns high and periodically remove conns expired after MCIT.

Configuring sql.DB pool in practice:
	- as a rule of thumb, explicitly set MaxOpenConns below db's max number of conns, and low enough to act as a throttle.
	- for a small-to-medium web apps and apis, maybe MaxOpenConns=25 (postgres' max_connetions=100). But, determine a suitable value from benchmarking and load-testing.
	- MaxIdleConns <= MaxOpenConns -> MaxIdleConns=25 cause generally, higher could mean more reusing conns.
	- to mitigate memory hoarding from high MaxIdleConns, set ConnMaxIdleTime=15min.
	- for now, postgres doesn't enfore a max conn lifetime, and this app doesn't have a load balancer before postgres, so leave MaxConnLifetime unlimited.
